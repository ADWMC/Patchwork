# 产品工程指南

## 定位

本指南是[可维护代码代理提示词](../assets/prompts/maintainable-coding-agent-prompt.md)
的产品维度增量。两者的关系：

- 可理解、可验证、可继续演进是**工程底盘**。不可维护的代码做不出可商业化的产品。
- 但可维护的代码不自动等于可商业化的产品。**用户好用、可商业化、方便商业化**
  是必须与职责拆分、命名规范同时成立的工程约束，不是写完代码之后的运营话题。

因此：目标用户假设、价值证据、分发路径，与模块边界一样，是一等设计输入。

"以用户身份走查、把体验差当缺陷"由 `/patchwork-review` 斜杠命令承载（见
[Agent 基础](agent-foundation.md)），作为站在用户立场评审代码的主入口；
本指南提供该评审背后的完整语境与验收标准。

## 一、用户好用

### 1. 目标用户必须显式

写任何产品前，先用三行说清：**谁**在**什么场景**下用它**替代什么**。
写不出来就先别写代码——那说明需求还不存在。

- 替代品盘点是必做项：用户今天用什么解决这个问题（包括“什么都不用/手工凑合”）。
  没有被替代对象的产品没有用户。
- 用户画像写入项目文档，与代码同步演进；被证伪就更新，不留着当装饰。

### 2. 验收以用户任务为标准

- 验收标准写成用户的任务结果，不是实现清单。“用户 5 分钟内完成首次导出”，
  而不是“导出接口返回 200”。
- **首次价值时间（time-to-value）是核心指标**：从用户拿到产品到得到第一次真实
  价值的步骤数与耗时。每多一步安装配置，就流失一批用户。
- 失败路径也是用户路径：报错文案写给用户看，说清发生了什么、用户该怎么办；
  堆栈和内部术语留给日志。

### 3. 反馈回路是产品代码的一部分

- 用户操作、失败、放弃点要可记录（本地日志或遥测，按隐私边界设计），否则
  “用户好用”永远只是作者的猜测。
- 汇报产品状态时使用与工程汇报相同的纪律：只报告可核实的数据
  （采纳率、完成率、耗时），不把“我觉得好用”当证据。

## 二、可商业化

### 1. 商业假设显式化

与“目标用户三行”并列，写清**谁付钱、为什么付、付给哪个具体能力**。
“以后总会想到办法赚钱”不是假设，是搁置；搁置的代价是架构里到处焊死了
免费假设（见三.2）。

### 2. 付费边界是架构边界

- 先区分**价值核心**与**付费能力**：免费部分必须独立完整可用（获客漏斗），
  付费能力通过清晰边界接入（独立模块、独立配置、可灰度启停）。
- 边界落到代码结构上：付费能力不散落在核心路径的 if 里，而是独立的
  能力模块 + 显式的授权检查点。这样商业模式切换（免费→收费→换收费点）
  不需要重构核心。

### 3. 价值必须可测，主张必须带数字

- 产品承诺用可测量的话说：“减少 X% 重复提示”，而不是“提升体验”。
- 没有数字之前不写进 README 承诺区；数字来自对照实验，不是感觉。
- 成本是商业变量：每次调用的 token/时间/资源开销要可见。价值减去成本
  才是用户净收益，成本不可见的产品定价无从谈起。

## 三、方便商业化

### 1. 分发即代码

- 安装步骤数是一等指标，和圈复杂度一样需要被优化。每加一步手工操作
  （复制文件、改配置、注册账号），当成一次架构妥协来审查。
- 从第一天起让安装、升级、卸载都是一条命令能完成的事；做不到就在
  文档里如实标注摩擦点，而不是藏在小字里。

### 2. 不要焊死商业假设

以下决策出现时留出边界，不提前实现，但也不让代码否决它们：

- **单机假设**：状态不全局散落，集中在可迁移的存储层，未来上云不必重写。
- **许可**：开源协议选择要意识到它决定（或排除）了哪些商业模式；MIT
  意味着“代码免费”是永久承诺，付费只能建立在代码之外（托管、支持、
  团队能力）。
- **密钥与授权**：授权检查点位置显式、集中，不与业务逻辑纠缠——既防
  绕过，也防未来换授权方案时伤及核心。

### 3. 表达层是产品代码

- 介绍语、README 首屏、报错文案按用户利益写，按“能落地的场景”写：
  说“你得到什么”，不说“我是什么”。
- 名称与命名规范同源：产品名、命令名、配置键、文档术语保持同一个概念
  一个名字。用户会把这些名字当 API 使用。

## 四、反模式

| 反模式 | 症状 | 纠正 |
|--------|------|------|
| Tech-demo 型 | 没有用户假设，没有替代品盘点，“先做出来再说” | 回到一.1，三行写不出不写代码 |
| 开源理想型 | 把一切商业考量当“庸俗”，架构焊死免费假设 | 回到二.1、三.2 |
| 过度商业型 | 核心功能上锁，体验被付费墙切碎，用户未得到价值先见到付费 | 付费边界只圈增量能力，核心完整可用 |
| 数字虚荣型 | README 写满承诺，没有任何可测证据 | 回到二.3，没有数字不承诺 |

## 五、每次开发前的四问

1. 目标用户是谁，替代品是什么？（写不出就停下）
2. 这次改动让首次价值时间变长还是变短？
3. 商业假设是否仍然成立，付费边界是否被这次改动模糊了？
4. 验收标准是用户的任务结果吗，可测吗？

四问中任何一问答不上来，先补答案再动代码——这与“修改前先调查”是同一条
纪律在产品维度的应用。

## 六、验收清单

交付产品代码时，除工程验收（职责边界、验证证据、文档同步）外，附加：

- [ ] 目标用户三行存在且与实现一致
- [ ] 首次价值路径亲自走过一遍，步骤数与文档一致
- [ ] 失败路径的用户文案可读、可行动
- [ ] 价值主张与实际度量一致，无未验证承诺
- [ ] 付费能力与核心的边界在代码结构上可辨认
- [ ] 安装/升级/卸载步骤数没有增加（增加了则有说明与理由）
