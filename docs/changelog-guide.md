# 更新日志指南

本指南用于 Patchwork 自身维护及 Agent 的变更收尾。依据与项目差异见[官方资料调研](changelog-research-2026-10-30.md)。维护其他仓库时，先读它的贡献规范和现有日志格式；本指南不要求所有项目都新建 `CHANGELOG.md`。

## 三种文档各回答一个问题

| 载体 | 读者要知道什么 | 应写内容 |
|---|---|---|
| [CHANGELOG](../CHANGELOG.md) / 项目既有 release notes | 这次变化对我有什么影响？ | 可见行为、兼容性、弃用/移除、必要迁移及影响升级的限制。 |
| README / 使用文档 | 现在怎么用？ | 安装、参数、默认值、示例、失败处理和迁移步骤。 |
| 验证 / 审计 / 实验报告 | 凭什么相信这个结果？ | 基准、环境、实际命令、失败、测量与未验证范围。 |

一份载体存在不代表另外两份已完成。普通调试日志也不能替代产品更新日志。

## 何时必须记录

判断对象是使用者、集成方或运维实际受到的影响，而非文件后缀或提交类型。以下变化应在同轮交付中记录：

- 新增或改变功能、UI 操作、工具/命令接口、参数、返回结果、错误处理。
- 改变默认值、配置位置、安装方法、依赖兼容范围、支持平台或资源要求。
- 修复已发布行为中的用户可见问题，包括权限隔离、数据保留、恢复和安全问题。
- 弃用、删除、破坏性变化、持久化格式或数据迁移，以及用户需要采取的动作。
- 改变 Agent 技能中的决策、交付要求或授权规则。技能虽是 Markdown，仍会改变产品行为；本次新增更新日志收尾规则就属于应记录的变化。

纯格式/错字、无行为变化的内部重构、测试补充通常可以不写。收尾时给出具体理由，例如“本轮仅修正示例中的错字，命令、默认值和行为未变，更新日志不适用”。文档修正若改变此前公布的兼容或使用承诺，应说明影响，不能一律豁免。

同一未发布功能的修正、回退或多次调优，更新原条目使其反映最终结果；不要把尚未发布的中间错误包装成多项产品修复。已有条目已准确覆盖本次变化时，核对后可以说明无需重复增加。

## 随实现维护，在交付前复核

1. **改前固定范围。** 找到既有规则、已发布基准与未发布区，确认本次任务边界和受影响读者。记录初始 dirty 状态，区分自己的改动与他人未完成工作。
2. **改中同步。** 行为、参数或迁移路径稳定后，同步使用文档和日志；后续方案改变时修正同一条，不留过时承诺。
3. **改后检查实际差异。** 同时核对 staged、unstaged 和 untracked 文件；只看提交历史会漏掉当前工作，只看 `git diff` 会漏掉未跟踪文件。保留无关改动，不擅自纳入本次成果。
4. **按用户结果合并。** 逐条追溯到实现、契约和真实验证；多个实现提交可合为一条，提交摘要只作为线索。发现弃用、移除、安全或迁移影响时单独复核。
5. **明确日志决定再交付。** 核对 README/使用文档和 CHANGELOG 的必要改动；汇报已更新的位置，或不适用/已被现有条目覆盖的具体理由。没有完成这一步，不把“测试通过”当作完整交付。

可先用以下只读命令盘点；对未跟踪文件还需实际打开检查：

```powershell
git status --short
git diff --stat
git diff --cached --stat
git ls-files --others --exclude-standard
```

对当前 Patchwork 的整体未发布区，可从已核实的 v0.2.0 基准审查；单次任务仍按它自己的初始状态划界。禁止为整理日志而 reset/clean 无关工作。

## 每条怎么写

一条说明一个可识别的结果，优先包含“触发场景或受影响对象 → 新行为/修复 → 必要行动”。准确写配置键、命令和默认值；内部实现映射放到报告。

| 不足的条目 | 可用的写法 |
|---|---|
| 优化隔离机制。 | 切走 Patchwork 后撤销专属工具与技能，保留的旧工具引用也不能继续调用。 |
| 修复 AF bug。 | 写入后接续命令返回非零退出码时，任务验收不再计为成功。 |
| UI 全面升级，体验更好。 | 侧栏日志支持按级别和机制筛选、搜索及 JSON 导出，并跟随 DSH 的浅深色外观。 |
| 文档更新。 | Agent 在交付前检查使用文档和更新日志；不适用时说明具体理由。 |
| 性能大幅提升，节省 50% token。 | 没有受控测量时删除该收益声明；可记录已经实现的具体行为，并链接实验范围。 |

以上示例取自当前 Patchwork 未发布变化，不是其他项目可以直接复用的事实。

类别沿用 Keep a Changelog 的语义，Patchwork 使用中文标题：新增（Added）、调整（Changed）、弃用（Deprecated）、移除（Removed）、修复（Fixed）、安全（Security）。省略空类。安全条目写已核实的影响和修复；没有已分配编号就不编造 CVE，也不要暴露密钥或可识别的会话数据。

迁移说明需要明确受影响安装/调用方、原行为、新行为和操作步骤。步骤较多时在 CHANGELOG 保留关键动作，再链接使用文档。不要用“存在兼容性调整”代替指引。

## 未发布、版本与日期

Patchwork 顶部使用 `## 未发布（Unreleased）`，只写已实现且属于范围的变化。计划和未验证收益留在方案/实验报告。当前版本为 `1.0.2`，编写日志不自动改变包版本。

准备实际发布时，核对交付范围、公共接口与兼容政策，再使用确定的版本和真实发布日期，把相应条目移入版本节；尚未交付的内容继续留在未发布区。`0.y.z` 是 SemVer 初始开发阶段，不能机械套用稳定版的 major 规则，但仍应明确披露不兼容变化。

不覆盖已发布版本的包内容；历史文字纠错可作澄清，但不能改写当时的事实。发布说明草稿、版本号选择、tag、提交、推送及发布是分别判断授权的动作。日志维护本身不授权后续操作。

以下仅为格式模板，尖括号不是待执行命令；正式条目不要保留占位符：

```markdown
## 未发布（Unreleased）

### 新增

- <受影响读者在什么场景下可以完成什么操作。>

### 修复

- <具体触发条件下，原错误行为如何被修正。>

### 升级注意

- <谁需要把哪个配置/调用从什么改成什么；链接迁移步骤。>
```

## 交付检查

- [ ] 已检查当前任务的完整差异，未混入无关 dirty 工作或遗漏 untracked 文件。
- [ ] 已判断用户、集成和运维影响；需要的条目随实现更新，豁免有具体理由。
- [ ] 每条可回查实际实现和证据；未把规划、旧测试或局部验证写成当前整体完成。
- [ ] 配置/默认值、权限、兼容、弃用、删除及升级动作与使用文档一致。
- [ ] 同一未发布变化已合并；版本、日期、发布状态及收益声明没有编造。
- [ ] 链接、文档结构和发行包内必须提供的文件已检查；收尾说明真实验证范围。

## 技能接线与当前边界

`patchwork` 给出收尾规则并导航；`documentation` 处理文档类型与来源；`standards` 判断收录/豁免；`anti-slop` 复核表达与事实；`evidence` 检查交付完整性。长篇调研不进入全局提示词，按需参考文件由技能入口链接；扩展目录仍只对 Patchwork Agent 可见。

当前采用人工维护，不新增日志生成器、fragment 系统或 CI 硬门禁。核对文件存在与否不能判断条目是否完整；技能规则也不能保证模型永不遗漏。今后若增加机械检查，仍需保留语义审查与明确的豁免方式。
