# Preset and Release Lessons

These lessons come from maintaining an agent preset alongside a host that
continues to evolve. They are technology-neutral design constraints for any
future Patchwork integration.

## Keep one source of truth

For each kind of data, choose one editable source and generate every derived
copy from it. Personas, host-derived configuration, package metadata, and
release artifacts should each have a clearly named owner. Generated outputs
must not become a second hand-edited source.

This avoids a common failure mode: a repository snapshot, installed copy, and
release archive gradually disagree while each appears locally plausible.

## Derive host-owned configuration from the host

Platform tool declarations belong to the host version that supplies them.
Copying or hand-maintaining those declarations creates configuration drift:
after a host upgrade, the agent may lose basic capabilities despite a valid
looking configuration.

When a host supports it, generate the agent configuration from the installed
standard configuration, replacing only the agent-owned portion such as its
persona. Validate that the generated row set matches the host's standard set
and record a content fingerprint to identify host upgrades versus local drift.

## Register capabilities in their narrowest scope

A capability package that registers agent tools or hooks should be mounted by
its agent preset, not globally by the profile. Duplicate or global registration
can prevent other presets from mounting. Establish ownership boundaries explicitly:

- The host preset owns host platform tools.
- The profile or bundle layer owns only genuinely shared host services.
- The agent preset owns its persona, selected host configuration, and agent-specific package.

Validate the assembled result in a real new session, not only by inspecting
YAML or JSON.

## Make generation idempotent

If generated bytes have not changed, do not rewrite the file. Some hosts use
file timestamps or sizes to decide whether to rebuild a live composition; a
no-op installer can otherwise trigger an unnecessary rebuild and surface
registration errors.

If generated content does change, document whether the host process must be
restarted before validating a new session. Treat a live-reload assumption as
an experiment, not a guarantee.

## Test the installation path users take

Repository checks are necessary but insufficient. A release-ready verification
should cover the actual distribution and installation path:

1. Build the intended archive from a clean or understood worktree.
2. Inspect the archive for required templates, scripts, and generated output.
3. Install it into an isolated or temporary host location.
4. Create a new session using the installed preset.
5. Confirm expected base tools are present.
6. Run one minimal real tool call, including the platform-specific shell path.

For Windows hosts, verify the available PowerShell tool directly. When WSL is
part of the supported workflow, verify it through PowerShell invoking
`wsl.exe`; do not assume an unrelated shell alias exists.

## Release with explicit evidence

Release automation should verify the exact assets it publishes. Check the tag,
asset count and names, stable download location when one is promised, and a
fresh installation of the released archive. Keep release checklists concise
but concrete: an omitted installer or stale archive is a product defect, not
administrative trivia.

## Preserve a short incident record

When an integration breaks, preserve the symptom, reproduction conditions,
root cause, repair, verification evidence, and the guardrail added afterward.
The goal is to prevent recurrence, not to preserve every exploratory command.
An incident record is especially valuable when the failure was caused by an
interaction between host versioning, cached state, generated configuration,
and installation order.
