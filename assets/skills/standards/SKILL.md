# Patchwork 工程收尾

**顺序**：安全与事实 → 用户授权 → 可验证正确 → 既有约定+最小改动 → 可维护表现。

**改前**：读调用方/配置/测试；事实 vs 推断 vs 未知；会改验收的歧义先问。

**改中**：最小正确改动；不为想象需求搭架子；不以 lint 代替行为验证。

代码清理只处理可定位的重复、死分支或无效抽象；先核实际入口、动态注册、Windows 路径与平台后缀。删除校验/try-catch 前说明谁承接错误；保留契约、安全、事务、兼容与有效测试。功能、取消、重试、部分成功和后续修改比行数或综合分重要。

**改后**：沿原失败路径验证；核使用文档与更新日志；只汇报跑过的命令与结果；未验证写明未验证。

**Git**：获得提交授权时，一逻辑一提交 `<type>(<scope>): <description>`；提交前相关测试 + `git diff --check`；**推送必须用户明确要求**。撤销、rebase/revert/reflog 或冲突处理读[Git 恢复与提交边界](references/git-recovery.md)。

职责与命名 → `architecture`。完成证据 → `evidence`。

## 文档与更新日志

先读当前项目的既有约定，改中维护，交付前专门复核；不强加新日志格式。核本任务 staged/unstaged/untracked，保留无关工作。
面向已交付产品的用户/集成/运维可见功能、接口、默认值、配置、权限、持久化、兼容、弃用/移除及迁移须同轮记录；技能 Markdown 改行为也适用。新增用户可见功能在 CHANGELOG 记新增与行为变化；使用方式或安装步骤变化再更新 README/指南。一次性预览或未采纳方案不写成已发布功能。
纯格式、测试、无行为变化的内部整理可豁免；收尾说明具体理由。已被条目准确覆盖则核对并说明，不重复增加。
README/使用文档写怎么用，更新日志写用户变化与升级动作，报告写验证。合并同一未发布变化，复核遗漏；条目表达 → `anti-slop`。
草稿保留未发布状态，不编版本/日期/收益；维护日志不授权改版本、tag、提交或发布。

## 技能与经验评估

失败/未知回执可用 patchwork_task candidate 记录任务内候选：来源、触发与动作；不是已学规则，不跨会话自动加载。
比较时固定模型、宿主/技能版本、初始工作区、预算和环境；调优集与留出集分离，先过正确性/后续维护，再比较成本/延迟，保存反例、退化与回退点。
分别记录路由是否触发、流程是否真实执行、产物是否改善；等长度文本分数或一次展示不等于编码能力提升。
实验档案用 `node scripts/check-evolution.mjs <experiment.json>` 检查资格；仅结构检查，不能证明提交的证据真实，更不会自动激活、提交、回退或发布。
