# 需求澄清清单

来源参考：[冰可乐的前端笔记 · Claude Code 提示词升级版](https://note.bingkele.cc/content/docs/41)。这里只保留可复用的提问角度，不复制原文，也不采用其中“无需确认即可读取任意文件”等扩大权限的写法。

## 何时使用

- 新功能、跨模块改动、多步骤任务；
- 用户描述含糊，或目标/范围/验收会因理解不同而改变；
- 需要委派给子代理，但任务边界还不清楚。

单一事实核查、小型只读回答不强制走这套清单。

## 一次集中问清

只在答案会改变交付时提问；能从代码/配置/既有约定推断的，不反问。

- **角色**：谁使用？有哪些角色和权限差异？
- **场景**：什么情况下使用？典型流程和触发入口？
- **数据**：输入输出是什么？数据量、来源、空值/异常形态？
- **性能**：响应时间、并发、预算或规模上限？
- **安全**：身份、权限、敏感数据、外部输入和副作用边界？
- **集成**：依赖哪些现有模块、接口、配置或外部系统？
- **边界**：失败、取消、重试、部分成功、迁移和回退怎么处理？
- **成功标准**：什么结果算完成？谁来验收？

## 输出结构

把回答整理成可执行的需求摘要：

1. 一句话目标；
2. 功能性需求（必需/可选）；
3. 非功能性需求（性能、安全、可用性、兼容性）；
4. 技术约束与依赖；
5. 风险与未知；
6. 需要用户决定的问题（附默认假设）；
7. 实现阶段（MVP / 后续）。

## Spec-driven 流程（大任务）

参考 [Spec Kit](https://github.com/github/spec-kit) 的最小流程，按需裁剪：

1. **constitution**：项目级原则（质量、测试、可维护性）；
2. **specify**：写清做什么、为什么、验收；
3. **plan**：技术方案、约束、风险；
4. **tasks**：拆成可独立验证的任务；
5. **implement**：按任务执行；
6. **converge**：对照 spec 检查偏差，修复后重复。

小任务不需要整套流程；多个独立子系统先拆 spec，不要塞进一个计划。spec 是事实源，计划/任务/实现偏离时要回写或明确说明。

## 纪律

- 区分“用户明确要求”“我们选择的实现”“仍未知”；不要把默认假设写成用户确认。
- 需求摘要可以进入 `patchwork_task brief`，但它不是权限，也不替代验收。
- 子代理只继承当前任务边界；不得从需求文本推断额外授权。
- 需求变更用 correct 更新受影响要求，旧证据重新核对。
