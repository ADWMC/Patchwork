# 代码评审

先确定范围和基线，读取完整差异、调用方、配置和相关测试；未跟踪文件与生成物要按实际影响纳入。沿受影响用户路径检查输入、状态、错误、取消、迁移和回退；不要只扫新增行。

每条发现写清触发条件、实际影响、证据、可用的文件行号和最小修正方向；按严重程度排序。只给了代码片段时不要编文件位置；未经测试的示例代码不要写成可直接使用的修复。事实不足时标为待核，不把风格偏好或静态模式命中报成 bug。若差异涉及身份、权限、外部内容、文件/网络副作用或秘密，读[信任边界](references/trust-boundaries.md)再检查。只在任务适用时检查商业或 UI 路径。

默认交付发现，不擅自修改被评审代码；若用户明确要求“不修改文件”，也不要为探针创建临时文件、复制源码或运行会写入文件的 shell 命令。必要的实验先说明会产生什么文件并取得范围许可；可用只读证据先核。用户明确要求边审边修时再实施，并区分已修复与未修复发现。没有发现也报告检查范围与未运行的路径。
