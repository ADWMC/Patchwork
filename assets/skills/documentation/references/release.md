# 版本与迁移

先确定已发布基线、未发布差异和实际包版本。更新日志条目说明受影响场景、改变后的行为、必要迁移动作；没有测量不要写性能收益。同一未发布功能的多次修正合并为最终状态，空类别不保留。

迁移说明至少核对旧配置/调用、新配置/调用、默认值变化、失败路径与回退方法。没有破坏性变化时不要编迁移步骤；有变化时不能只写“请升级”。版本、日期、tag、发布动作必须来自实际状态，编写文档本身不授权发布。

Patchwork 自身项目还应按 `docs/changelog-guide.md` 的实际仓库规则维护；为其他项目写文档时，以目标项目的约定为准。

## 根据读者选择载体

| 用户要知道 | 优先写入 | 核验来源 |
| --- | --- | --- |
| 如何安装、启用、回退 | README / 使用指南 | 包内文件、真实命令、配置默认值 |
| 已有用户升级后会变什么 | CHANGELOG / release notes | 已发布基线与当前实现差异 |
| 为什么相信效果或限制 | 执行/实验记录 | 原始任务、环境、失败、测量与验收 |

一个行为同时需要三种说明时，用链接连接而非重复整段。Patchwork 的技能目录例子：README 应写默认目录与 `skillsMode: core` 回退方法；CHANGELOG 记用户可见的新增/调整；实验报告保留真实 DSH 调用和“尚未证明净收益”的范围。

## 迁移段落的最小结构

明确列出**受影响者、旧行为、新行为、要改的配置或调用、失败时的回退**。逐项从代码或真实包核对名称与默认值。若旧用户无需操作，直接说无需操作，不虚构迁移步骤。对于删除/弃用，说明开始影响的版本或日期；未知时标为未定，不写猜测值。

交付前检查相对链接、包内是否包含引用文件、示例命令是否仍可执行，以及“所有/从不/提升”等高强度断言是否有相应证据。只读实验不能推出正式发布；编辑 CHANGELOG 也不等于已经打 tag 或推送。
