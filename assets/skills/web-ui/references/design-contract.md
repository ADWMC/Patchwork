# Web UI 设计契约

用于新页面、大改版、设计方向不明或既有产品的视觉判断。它是取证模板，不是让模型凭感觉填写的风格问卷。明确的小改动只核对受影响的约束。

## 证据优先级

1. 用户给定的目标、品牌资产、参考与交付范围。
2. 目标仓库实际运行中的页面、组件、语义 token、字体、主题和布局容器。
3. 已有设计系统与设计记录；先核对它们是否与当前代码一致。
4. 可访问的参考截图、产品资料和行业惯例。
5. 模型提出的新选择。它必须写明假设，不能伪装成既定品牌或用户研究。

冲突时记录“来源 → 值/行为 → 适用页面 → 取舍”，不要靠偏好投票。用户要求复制参考视觉时，先确认资产与授权边界；未知品牌色、真实指标或用户画像保持未知。

## 最小设计输入

| 项 | 应找到的证据 | 缺失时的做法 |
| --- | --- | --- |
| 任务 | 用户要完成的主动作、阅读或决策 | 用一句可检验的任务描述标出假设；会改变范围时询问 |
| 内容 | 真实标题、对象、状态、操作与数据 schema | 使用清楚标注的样例，不伪造遥测、客户或效果数字 |
| 容器 | 实际视口、嵌入位置、导航和可用宽度 | 先测或截图；不能仅按整页桌面宽度设计侧栏 |
| 系统 | 字体、间距、色彩角色、圆角、图标、浅深色来源 | 先复用现有语义 token；没有系统时才提出最小新集合 |
| 素材 | Logo、产品图、截图、插画的真实来源 | 缺主视觉素材时先确认可获得性，不把低质占位物当最终品 |

设计提案只需说明主对象、主操作、信息层级、版式关系、字色系统和一处有意义的特色。对操作型界面，首先保证扫描、比较和重复使用效率；营销页可以把叙事和气氛放在更高位置。选现成设计系统或风格资料时，先映射到当前产品的内容、组件和 token，不能因为资料库推荐就覆盖已批准的品牌。

**设计记录不是页面文案。** “简化大陆 · 日照明暗 · 星空”这类实现或效果清单可在会话中说明，不应自动变成页面副标题。逐段检查可见文字：用户在页面内读到它，是否更容易识别对象、完成动作或理解真实状态？若只是解释制作方法或替作品自评，就从 UI 删除，并放到交付说明。操作提示只在发现性确有需要时保留，且用动作语言而非功能列表。

参考做法：OpenDesign 将 `DESIGN.md`、`tokens.css`、组件样例与来源拆成可核对的设计系统包；这里借用“契约与产物分离”的方法，不复制其品牌包。来源：https://github.com/nexu-io/open-design/blob/main/docs/design-systems.md
