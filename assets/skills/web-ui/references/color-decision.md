# Web UI 配色决策

用于需要选色、改色、建立主题或评价配色的 UI 任务。局部修改只检查受影响的颜色角色和组件；已有产品先取证现行 token，不因“更特别”替换品牌色。

## 先找颜色的来源和职责

按顺序核对用户指定的品牌/参考、产品实际 CSS 或设计系统、宿主主题 token、目标页面的真实内容。区分已批准的值、当前代码中的值和模型提出的候选；冲突时说明来源与取舍。Patchwork 自身侧栏沿用 DSH 语义 token 和浅深色，不另建一套固定品牌色。新产品没有设计系统时，才建立满足当前任务的最小颜色集合。

先给每个**必要角色**命名：页面和层级表面、正文和次要文字、主要动作及其文字、链接、边框/分隔、焦点、成功/警告/错误。一个色值可以复用，但相似颜色若同时表示“可点击”和“纯装饰”，需要检查是否会混淆。状态不只靠颜色传达，必须还有文字、形状或控件状态。色板 CSV、行业配色和所谓禁色表只能提出候选，不能替代这些语义决定。

## 候选色必须成对验证

对实际要相邻呈现的前景/背景色对记录色值、用途和对比度；不要只列“主色/辅色/CTA”。至少核对正文、按钮文字、次要文字、链接、焦点和关键控件边界。普通文字以 WCAG 2.2 AA 的 4.5:1、大文字以 3:1 为下限；识别控件或状态必需的非文字信息按 3:1 检查，阈值比较不四舍五入。比值合格只证明一个可读性条件，不证明整体颜色好看或品牌适合。

透明度、叠层、图片、渐变或动态背景会改变实际色对：能从最终像素和来源求值才报精确比值；无法确定时标明待测，不能凭截图猜出 HEX 后宣称通过。定义浅色、暗色与现有增强对比模式的对应关系，并查看常态、悬停、按下、选中、禁用、加载、错误和焦点中适用的状态；不要求每个控件虚构全部状态。

## 看画面而不是只看比值

在目标容器和关键状态渲染后，先观察大面积色块、视觉主次、操作是否突出、状态色是否抢走内容注意力，再检查真实设备或浏览器的浅深色。若去色后结构仍混乱，先修结构；若所有元素都在用强调色，减少强调对象。审查建议给出位置、原色/候选色、真实相邻色对和理由。颜色取舍留在会话或设计记录，别写成页面说明文案。

需要记录方案时，用小表即可：`角色 | 来源/语义 | 浅色值与色对 | 暗色值与色对 | 状态 | 测量/待验证`。局部修复只记录改动的几行；不要求每个页面输出完整色彩规范。

方法参考：[Apple 官方 Color](https://developer.apple.com/design/human-interface-guidelines/color)、WCAG 2.2 的[文字对比度](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)与[非文字对比度](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)、[Design Tokens Community Group 2025.10](https://www.designtokens.org/TR/2025.10/format/)。借鉴语义和验证流程，不复制第三方色板或 Apple 平台专属 API。
