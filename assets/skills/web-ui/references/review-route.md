# Web UI 资料路由与分层审查

用于新页、整体改版和需要完整评审的页面。明确的小修复只按改动范围取证和复核。先读用户要求与当前产品，再挑相关资料；不要把每份参考文件都装进上下文。

## 按任务加载

| 当前任务或画面 | 优先资料与检查 |
| --- | --- |
| 新页或大改版 | [设计契约](design-contract.md)：用户任务、真实内容、容器、已有系统与不确定点；必要时画两个组织逻辑不同的低保真方向。 |
| 用户指出模板味或结构重复 | [去模板味复核](anti-template.md)：对象关系、等权卡片、重复状态、无任务用途的说明和空白。 |
| 配色、主题、状态色或视觉一致性 | [配色决策](color-decision.md)：语义角色、浅深色、前景/背景色对、实际画面。 |
| 交付前或声称“完成” | [验证矩阵](verification.md)：真实任务、边界数据、目标尺寸、状态、键盘、运行和截图。 |

只读取当前任务需要的产品代码、组件、token 和参考。外部资料可帮助提出问题，不能覆盖已批准的品牌或宿主惯例。截图、源码、设计记录和用户反馈各自能证明的事情不同；缺少某种证据时标明限制。

## 五个审查镜头

1. **可访问性：**文字与控件色对、焦点、语义名称、键盘、缩放及颜色以外的状态表达。能测量的给数值，不能从 JPEG 猜尺寸或对比度。
2. **产品/宿主惯例：**导航、组件、token、主题、操作位置是否与当前产品一致。Web 插件按宿主 WebUI 评审，不套用 iOS tab bar、系统色 API 或触控点数。
3. **视觉工艺：**信息层级、密度、对齐、字阶、色彩职责、主对象和产品特异性。先描述实际渲染，再判断；不为求新奇强加特色。已成立的决定也要保留。
4. **交互：**主任务、等待/失败/恢复、撤销或重试、不同输入方式与真实状态。源码推断和实际操作分开记录。
5. **内容文案：**对象名称、操作标签、状态、错误下一步与边界内容；删掉制作说明、自评和无助于任务的副标题。

对每个重要发现写清 `看到什么 | 依据和用户影响 | 具体改法 | 证据/未验证`。先处理阻断任务和可访问性的缺陷，再处理产品一致性、视觉结构与打磨；不要用模型自评分代替用户审美判断。报告简短地列出应保留的优点，避免整页被无依据地重做。

改版时先给出可逆的设计决定和最小代表性画面；实际渲染后复看，再按用户纠正迭代。完整方案和审查结论留在会话或工作记录，不自动出现在产品页面。

方法参考社区 [`apple-design-skill`](https://github.com/dickwu/apple-design-skill/blob/ff4ebddf0488598723a82bfdce1afb04de0b1c44/SKILL.md)的按需资料路由与分层审查，以及 [Apple 官方设计原则](https://developer.apple.com/design/human-interface-guidelines/design-principles)。这里为 Web 产品重写流程，不复制其打包的 Apple HIG 正文。
