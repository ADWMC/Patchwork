# Web / UI 设计

把「能运行」「好使用」「好看」分开判断。用户指定的品牌、参考、结构和交付范围优先；不能凭一次构建成功或交互通过宣称视觉完成。

## 选择工作路径

- **明确的小改动**：只改点名的元素，沿现有组件与样式；改了视觉就在目标尺寸看改动处。不要为一个按钮重做整页。
- **新页面或整体改版**：先确定方向和主视口，再实现代表性画面、查看截图、修正最明显的问题。用户只要方案或评审时，不擅自实装。
- **现有产品**：先读入口、布局、真实组件、语义 tokens、字体、主题和设计记录，核对目标页现状画面。沿用已成立的规则，只替换造成问题的默认值。

新页/改版先看[资料路由](references/review-route.md)与[设计契约](references/design-contract.md)；布局读[布局](references/layout.md)；可访问性读[可访问性](references/accessibility-motion.md)；配色/主题读[配色决策](references/color-decision.md)；模板味读[反模板](references/anti-template.md)；交付前读[验证矩阵](references/verification.md)。

## 新设计先作决定

1. 判断这块界面供操作、阅读、决策还是体验；操作页优先扫描与熟悉交互。写清用户、主任务、真实内容、主设备和限制；未知标为未知，不能伪造遥测。
2. 用一句话定视觉方向：首屏主角、主动作、版式关系，以及字体、色板和材质为何适合这个对象。选一处有辨识度的表现，其余退后。写出要删、合并或降级的装饰和重复说明。
3. 对新页或大改版，先用灰度结构检查视线顺序、主角尺度、操作位置和内容密度；结构不成立时先改结构。需要主视觉素材时先确定来源与可实现性，不能拿低质量占位物当最终效果。
4. 先按任务决定内容组织方式，再选卡片、列表或表格。默认的等宽卡片、徽章、装饰图标和说明横幅若不能解释对象关系，就改变结构；换色不算去模板味。

## 实现与验证

- 页面文字只服务对象识别、操作和真实状态；按钮说动作，空态和错误给下一步。设计理由、效果清单与验收结论留在会话，不写成页面副标题。细节读设计契约，表达可按需加载 `anti-slop`。
- 核心动作走真实路径；按压、等待、完成和失败有及时反馈。控件先用原生语义，再用现有可访问组件；检查表单标签、图标按钮名称及键盘焦点，弹层与触发点保持空间关系。
- 动效按频率、目的和可中断性选；沿用现有 token，简单状态用 CSS，手势才用 JS。重复触发从当前状态接续，进出路径一致；优先 `transform`/`opacity`，避免 `transition: all`；兼顾减少动态效果偏好，悬停动效只给支持 hover 的设备。
- 用符合数据契约的样例检查长/短文本、缺字段、零/单条/大量结果、极端数字和翻译文案；边界数据经原数据入口注入，不为测试手改组件内容。
- 在实际目标尺寸看首屏和关键状态的截图：先问第一眼看到的是否是主角，再查比例、裁切、对比、字体、重复装饰和溢出。新页至少据截图做一次明确的保留或修改判断；若有明显缺陷，修完复看。动态或 3D 主视觉还要实际操作，不能只凭静图。
- 分开报告源码检查、真实渲染、几何/溢出和交互证据；审查发现给出文件位置、影响和修正建议。性能/无障碍评分不代替任务与视觉判断。无法看图或运行时明说未验证；完成证据可再加载 `evidence`，目录职责变化才加载 `architecture`。
