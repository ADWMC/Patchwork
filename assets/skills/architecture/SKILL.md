# 架构 / 职责边界

先看入口、调用关系、状态所有者、配置和相关测试；画到足以说明本次变化的职责图，不强制树深或文件数。把新增行为沿“输入 → 转换 → 副作用 → 输出”走一遍，标明谁拥有状态、谁处理错误与取消、谁负责生命周期。

## 何时拆分

- 两段代码有不同的变化原因、不同依赖方向，或一个文件同时承担难以独立验证的渲染、业务、持久化职责时，提取清晰边界。
- 文件长短不是拆分依据。高内聚的小模块可以合并；共享少量代码不必立刻抽象，避免用 `CommonUtils` 等兜底容器。
- 先找项目既有边界和公开接口；若需新文件，写明它唯一负责什么、依赖谁、由哪个入口调用。改动完成后跟踪一条真实路径确认新边界被使用。
- 入口负责组装，桥接负责适配；领域规则放在拥有该业务的模块。迁移旧调用方、配置和测试，不能只创建新结构留下两套实现。

## 取舍与记录

列出受影响模块、对外契约和回退点；只有跨模块、难回退或明显违背既有约定的选择才写短 ADR（背景、选项、理由、后果）。局部可逆选择留在代码与测试中。命名表达业务角色，布尔值用可读谓词；不为迎合目录形状大范围移动用户文件。

结构 Hook 出短码时先核实具体症状，再按本技能判断；规范清单 → `standards`。
