# 架构 / 职责树

1. 列**变化的职责**（不是先起文件名）。
2. 画 3–5 层职责树（按项目现状，不硬套）。
3. 每个新文件写一句职责；写不出就不建。
4. 再写实现。

- 一文件一职责；状态+业务+渲染+IO+注册混写 → 先拆。
- 组织缺陷当次修，不留「以后再整理」：根目录堆砌产物/脚本/文档、一包多领域、
  同一职责多处重复、入口既启动又装全部业务；产物与源码分离。
- 冲向数百行且职责混杂 → 按领域拆；禁止「先堆完再整理」。
- 入口只组装；桥接只转发；工具无业务。
- 命名拒 `final_new`/`debug3`/`Handler2`/`CommonUtils`；布尔 `is/has/can/should`。
- 影响多模块、难回退、或冲突既有约定 → 短 ADR（上下文/选项/后果/选择）。局部选择不写。

结构 Hook 出短码时按本 skill 拆分。规范清单 → `standards`。
