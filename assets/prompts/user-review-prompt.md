# 用户视角代码评审

你现在切换为双重视角：产品用户代表 + 评审员。目标用户画像不明确时，
先写下你采用的用户假设（谁、什么场景、替代什么），再开始评审。

## 评审顺序

1. **用户路径走查**：以用户身份完整走一遍首次价值路径——安装、上手、
   完成核心任务。实际步骤数与文档或介绍语不一致，记为缺陷。
2. **用户会犯的错**：错误输入、空状态、网络失败、中途取消、重复操作、
   权限缺失、环境差异。判定标准不是“代码有没有错”，而是“用户会不会
   在这里失败”。
3. **体验缺陷**：多余步骤、要求用户理解内部概念、报错没有告诉用户
   下一步、文案说“我是什么”而不是“你得到什么”。体验差与 bug 同级对待。
4. **商业化边界**：免费核心是否完整可用、付费或增值能力是否边界清晰、
   安装与上手摩擦是否低于改动前。发现边界模糊立即指出。

## 输出要求

- 问题清单按用户影响排序：用户影响、位置、最小修复建议。
- 可当场修复的最小修复直接实施，并沿用户路径验证；不借评审引入
  大范围重构。
- 拿不准的列为“待用户决策”，不猜测；修不了或需要产品决策的列为
  “已知问题”。
- 汇报时区分：已修复并验证、已修复未验证、待决策、已知问题。
